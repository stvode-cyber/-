# 远程电脑助手方案设计（阶段化：定位 / 模块 / 选型 / 路线图）

> 版本：v1.0 ｜ 日期：2026-08-12 ｜ 状态：方案设计稿（纯文档，未实现）
> 设计锚点：**复用 DAM-lite 的「特定区远程提取」安全基座**（设备绑定 + 二次验证 + 强制确认闭环 + 双权限等级），在其上叠加微信 / 邮件指令通道与 AI 进度推送，构成"确认继续运行"的远程控制闭环。
> 授权发件邮箱：`guanliyuan@mushenglin.cn`（安全防护核心白名单）。

## 一、定位（Positioning）

### 1.1 是什么
远程电脑助手是一套**远程控制平面**：用户通过**微信 / 邮件**向本机下达指令，系统在本机执行并**由 AI 推送工作进度**，对高风险动作要求用户**确认才继续运行**——形成"指令 → 执行 → 进度 → 确认 → 继续/中止"的闭环控制。

### 1.2 与 DAM-lite 的关系（架构连续性）
DAM-lite 的 **M6 特定区远程提取** 已落地：设备绑定（`ExecInstance`）、二次验证（step-up）、双权限等级（`specified_zone` / `full_instance`）、触发→确认→执行闭环、实例令牌可吊销。远程电脑助手**直接复用这套安全基座**作为"执行面"，新增的只是**控制面（消息通道）**与**进度面（AI 推送）**。不重复造安全轮子。

### 1.3 服务谁 / 解决什么
| 角色 | 场景 |
|------|------|
| 本人（机主） | 不在电脑前时，用微信/邮件让本机跑指定任务，随时看进度、风险动作需本人确认 |
| 授权协作者 | 经 `guanliyuan@mushenglin.cn` 授权邮箱白名单 + 空间权限，在限定范围内远程触发 |

### 1.4 设计原则
1. **默认不自动执行高危动作**：一切涉及文件/系统/网络的高风险操作，必须"确认继续运行"。
2. **身份先于指令**：指令来源必须经授权通道鉴权（授权邮箱白名单 / 微信绑定身份），否则丢弃。
3. **可审计、可熔断**：每条指令与确认留痕；提供一键挂起/熔断开关。
4. **复用既有安全基座**：不新建鉴权体系，沿用 M6 的设备绑定与 step-up。

## 二、模块（Modules）

### M1 指令通道接入（控制面）
- **邮件通道**：监听授权邮箱 `guanliyuan@mushenglin.cn`（IMAP 拉取 / 转发 webhook），仅处理**发件人在白名单内**的邮件；主题/正文解析为结构化指令（`action` + `params` + `spaceId`）。
- **微信通道**：经企业微信/公众号 webhook 或微信开放平台回调接收文本指令；微信身份绑定到本机用户（绑定后签发长期身份令牌）。
- **指令网关**：统一做来源鉴权 → 指令解析 → 风险分级 → 入队（`FetchJob`/指令任务表）。

### M2 指令执行引擎（执行面，复用 M6）
- **沙箱化执行**：指令实际在本机 agent（复用 Electron/桌面端进程）执行，受 `ResourceZone.fetchScope` 边界约束。
- **双权限等级**：
  - `specified_zone`（指定区域）：仅能在登记的资源区内操作；触发者对该空间有写权限即可。
  - `full_instance`（全电脑，高危）：涉及整实例；**强制要求触发者为空间 owner**，且**每次强制本地确认**。
- **执行即入库**：文件类结果走 `POST /assets/sync` 进入 DAM-lite 资产库（与采集链路同源）。

### M3 进度推送（进度面，AI 生成）
- **进度采集**：执行过程产出结构化事件（开始/进度%/阶段性产物/异常）。
- **AI 摘要**：用 LLM 把原始事件压缩为自然语言进度摘要（如"已处理 12/40 个文件，预计还需 2 分钟"），避免刷屏。
- **按通道回推**：原指令来自微信 → 推微信；来自邮件 → 回邮件；支持"仅关键节点推送"开关。

### M4 确认继续运行闭环（核心安全控制）
- **风险判定**：指令/子步骤被标注风险等级（低/中/高）。中风险可批量确认，高风险**必须逐条确认**。
- **挂起等待**：到达需确认节点时，执行**挂起**，向用户推送确认请求（含动作摘要 + 影响范围）。
- **确认即续跑**：用户回复"继续/确认"（微信关键词或邮件回复）→ 解除挂起，继续执行；**超时（默认 30 分钟）自动中止并回滚未完成部分**。
- **中止/熔断**：用户回复"停止/中止"→ 立即终止；全局"远程助手熔断开关"一键关闭所有在途任务。

### M5 安全防护（贯穿）
- **授权发件邮箱白名单**：仅 `guanliyuan@mushenglin.cn` 及显式追加的授权地址可被邮件通道受理；其余一律丢弃且不回执。
- **二次验证（step-up）**：触发 `full_instance` 或高风险指令前，需密码重校验签发 5 分钟短令牌。
- **设备绑定 + 令牌吊销**：执行端实例（`ExecInstance`）指纹 + 令牌（30 天 TTL、可解绑吊销）；泄漏可立即失效。
- **审计日志**：指令来源、解析结果、确认动作、执行结果全量留痕（含 IP/UA）。
- **防指令注入**：邮件/微信正文按"数据"对待，指令关键字仅来自预定义动作表，禁止正文拼接出任意系统命令（防 RCE）。

## 三、选型（Tech Selection）

### 3.1 复用层（已落地，来自 DAM-lite M6）
| 能力 | 实现 | 来源 |
|------|------|------|
| 设备绑定 | `ExecInstance`（指纹 + 实例令牌 + TTL + 吊销） | `remoteFetch.routes.ts` / `schema.prisma` |
| 二次验证 | `POST /remote-fetch/step-up`（密码重校验 → 5min 短令牌） | 同上 |
| 双权限等级 | `ResourceZone.fetchScope`：`specified_zone` / `full_instance` | 同上 |
| 触发→确认→执行 | `fetch` → 实例拉取 → `confirm` → `execute` | 同上 |
| 鉴权链 | `authRequired` → `requireStepUp` → `instanceAuth` | 同上 |

### 3.2 新增层（本方案范围）
| 层 | 选型 | 说明 |
|----|------|------|
| 邮件通道 | **IMAP 拉取 + SMTP 发送**（Node `imap`/`nodemailer`），授权邮箱白名单校验 | 低依赖、可自托管 |
| 微信通道 | **企业微信 webhook / 公众号模板消息 + 回调** | 机主微信身份绑定到本机用户 |
| 指令解析 | 正则/关键词 → 预定义动作表（`action` 白名单） | 防注入，禁用任意命令执行 |
| 进度 AI 摘要 | LLM 文本压缩（可走本地轻量模型或云端，进度摘要非敏感时可云端） | 自然语言压缩，避免刷屏 |
| 执行端 | 复用 **Electron 桌面端 agent**（与 DAM-lite 采集端同进程） | 共享 FS 能力与 `ResourceZone` 边界 |
| 任务状态 | 复用 `FetchJob`（扩展 `channel` / `needConfirm` / `confirmStatus` 字段） | 不新建任务表 |

### 3.3 安全选型理由
- **复用 M6 而非新建**：设备绑定/step-up/双权限已在代码与冒烟中验证（见 `DAM_INTEGRATION.md`），新建只会增加攻击面。
- **指令白名单而非自由命令**：远程助手最大风险是"邮件正文变成 shell"，故指令必须落在预定义 `action` 表，参数经严格校验。
- **确认继续运行超时中止**：防止"发了指令人走开"导致危险操作无人兜底，超时自动回滚未完成部分。

## 四、路线图（Roadmap）

### P0 · 安全基座对齐（✅ 已具备，来自 DAM-lite M6）
- 设备绑定、step-up 二次验证、双权限等级、触发→确认→执行闭环、令牌吊销：**已实现并冒烟验证**。
- 本阶段任务：明确"远程电脑助手"复用 M6 的接口契约，不写新安全代码。

### P1 · 邮件通道闭环（落地清单，建议起点）
> 目标：用最小通道（邮件）打通"指令→执行→进度→确认继续运行"全闭环，全程复用 M6 安全基座。

**P1-1 邮件通道接入（授权邮箱白名单）**
- 拉取：Node `imap` 轮询/IDLE 监听 `guanliyuan@mushenglin.cn` 收件箱；仅处理**发件人在授权白名单**的邮件（白名单表初始仅该邮箱 + 显式追加项），其余静默丢弃且不回执。
- 发送：`nodemailer` SMTP 回推进度/确认请求；凭据存**系统密钥库**（禁止硬编码/落库明文）。
- 入参：`subject`/`body` 解析为 `{ action, params, spaceId, channel:'email' }`。
- 验收：非白名单发件邮件被忽略；白名单邮件正确解析为指令任务并落 `FetchJob`。

**P1-2 指令网关（解析 + 风险分级 + 入队）**
- 解析：邮件正文按正则映射到**预定义 `action` 白名单**（如 `extract`/`organize`/`fetch_category`），参数严格校验（路径必须在 `ResourceZone` 边界内）。
- 风险分级：每 action 标注 低/中/高；高风险强制 `needConfirm=true` 且 `fetchScope=full_instance` 时要求触发者为 owner。
- 入队：扩展 `FetchJob` 增加 `channel` / `needConfirm` / `confirmStatus`（pending/confirmed/aborted）；触发走 M6 的 `resource-zones/:id/fetch`（带 step-up）。
- 防指令注入：正文作"数据"处理，禁止拼接出任意系统命令（禁用 `eval`/shell 透传），action 仅取白名单。
- 验收：非法 action 被拒；高风险指令落库为 `needConfirm=pending`；参数越界（超出资源区）被拦。

**P1-3 确认继续运行闭环**
- 挂起：执行到需确认节点 → 经 SMTP 推送确认请求（含动作摘要 + 影响范围 + 回复"继续/停止"指引）→ 执行挂起。
- 续跑：解析用户回复邮件关键词（继续/确认/停止）→ `confirm` 解除挂起继续；`stop`/超时（默认 30min）自动 `aborted` 并回滚未完成部分。
- 验收：高风险动作不自动执行；回复"继续"后执行推进；超时未确认自动中止且状态正确。

**P1-4 AI 进度摘要回推**
- 采集：执行端产出结构化事件（开始/进度%/产物/异常）。
- 摘要：LLM 把事件压缩为自然语言（如"已处理 12/40，预计 2 分钟"）；进度摘要非敏感时可走云端 LLM。
- 回推：按 `channel='email'` 经 SMTP 回原指令邮箱；支持"仅关键节点"开关（开始/完成/需确认/异常）。
- 验收：邮件收到可读进度摘要；高频事件不过度刷屏。

**P1 退出标准**：邮件通道收/发打通 + 白名单鉴权生效 + 至少 1 个高风险 action 走通"确认继续运行"闭环 + AI 进度摘要回邮件 + 防注入规则覆盖冒烟。

### P2 · 微信通道（落地清单）
> 目标：在 P1 邮件闭环之上，新增微信作为第二控制面，复用同一指令网关、同一 M6 安全基座、同一"确认继续运行"状态机。

**P2-1 微信通道接入（webhook + 机主绑定）**
- 接入：企业微信/公众号 webhook 接收文本消息；机主身份经"绑定验证码"机制绑定（首次发送 `/bind` 触发一次性码，回填确认），避免任意微信账号冒充。
- 通道适配：扩展 P1-1 的 `{ action, params, spaceId, channel }` 解析，新增 `channel:'wechat'`；白名单鉴权复用（绑定后的微信 openid 入白名单）。
- 验收：非绑定微信消息被忽略；绑定后微信消息正确解析为 `FetchJob`；与邮件通道共用白名单表。
- 涉及文件：`backend/src/routes/remote-fetch/wechat.routes.ts`（新增）、`FetchJob.channel` 枚举扩展、`whitelist` 表增 `channel/openid`。

**P2-2 微信端确认继续运行**
- 复用 P1-3 的"确认继续运行"状态机（pending/confirmed/aborted），仅通知通道由 SMTP 改为微信模板/文本消息。
- 关键词：回复"继续/确认"→ `confirm`；"停止"→ `aborted`；超时（默认 30min）自动中止回滚（逻辑与邮件完全一致，单份实现、双通道触发）。
- 验收：高风险动作微信端触发确认；回复"继续"后执行推进；超时逻辑与邮件共用、行为一致。

**P2-3 进度按需推微信**
- 复用 P1-4 的 LLM 进度摘要，通道路由增加 `wechat`：按 `channel` 选择 SMTP 或微信推送；保留"仅关键节点"开关。
- 验收：微信收到可读进度摘要；高频事件不刷屏；与邮件推送同源摘要、格式适配微信。
- 涉及文件：`backend/src/lib/notify.ts`（通道路由，新增 wechat 分支）。

**P2 退出标准**：微信通道收/发打通 + 绑定鉴权生效 + 微信端走通"确认继续运行"闭环 + 进度推微信 + 与邮件通道共用同一安全/状态机无分叉。
**P2 风险**：微信 webhook 回调地址公网可达性与签名校验、模板消息频率限制、机主绑定码泄露。

### P3 · 多指令类型与策略引擎（落地清单）
> 目标：在 P1 邮件 / P2 微信双通道之上，扩展指令广度并引入策略自动化，仍全程复用 M6 安全基座。

**P3-1 扩展指令动作表**
- 新增 action：`organize`（按规则重排目录）、`extract_category`（提取某分类资产打包）、`batch_rename`（批量重命名，含模板变量）、`report`（生成资产/分类统计报告）、`sync_now`（强制触发同步）。
- 每个 action 复用 P1-2 的白名单解析 + 风险分级；参数严格校验（路径边界、模板安全防注入）。
- 验收：各 action 经邮件/微信触发并正确执行；非法模板变量被拒。
- 涉及文件：`backend/src/routes/remote-fetch/actions/*.ts`（新增，每 action 一个处理器）、`actionRegistry`。

**P3-2 策略引擎（自动放行 / 需确认 / 禁止）**
- 策略维度：发件人/微信 openid / 空间 / 时间窗 / action 类型；命中"自动放行"跳过确认（仅低风险）、"需确认"走 P1-3、"禁止"直接拒绝并审计告警。
- 策略存储：DB 表 `fetch_policy`（owner 可增删改），默认拒绝（fail-closed）。
- 验收：配置"白名单邮箱 + extract 自动放行"后免确认；"禁止"策略拦截对应指令并留审计。
- 涉及文件：`backend/src/routes/remote-fetch/policy.ts`（新增）、`FetchJob` 增 `policyId`、管理端 UI。

**P3-3 应急熔断与审计看板**
- 熔断：连续 N 次执行异常 / 单位时间内指令激增 → 自动熔断（暂停新指令、通知 owner），手动恢复。
- 审计看板：所有指令/确认/执行/异常的时间线视图（含通道、action、影响范围、操作人），支持导出。
- 验收：注入异常触发熔断；审计看板可回溯任意指令全链路。
- 涉及文件：`backend/src/lib/breaker.ts`（新增）、`frontend` 审计页。

**P3 退出标准**：指令动作表扩展 ≥4 类且双通道可用 + 策略引擎驱动放行/确认/禁止 + 熔断与审计看板上线。
**P3 风险**：策略误配导致误放行、熔断误伤正常指令、审计数据量增长。
